# AE-088: Manual Allocation Reassignment

## Overview

Implemented a manual reassignment API that allows authorized professors or administrators to reassign a single allocation row to another eligible Teaching Assistant (TA).

## Implemented Changes

### 1. Allocation Reassignment Service Method
- Implemented `AllocationService.reassignAllocation(...)` to handle manual reassignments.
- The service wraps all operations in a database transaction using `runInTransaction`.
- Performs validations:
  - Formats of all raw IDs (Exam, Allocation, Target TA, Acting User).
  - Target TA must belong to the course of the exam.
  - Cross-resource verification: ensures the target allocation is indeed associated with the specified exam.
  - Conflict check: checks if the target TA is already assigned to the same answer script and question, avoiding duplication conflicts.
- Mutates the allocation TA field and saves the document to trigger pre-save schema validation (guarding against mixed whole-script/question-wise grading modes).

### 2. Transaction Auditing
- Logs an `ALLOCATION_REASSIGN` audit entry with type `SUCCESS` directly inside the transaction database session.
- Records key context details: `examId`, `answerScriptId`, `question`, `previousTaId`, and `newTaId`.

### 3. Reassignment PUT Endpoint
- Created `PUT /api/exams/[id]/allocate/reassign` with:
  - Permission gate: checks `Permission.ALLOCATE_SCRIPTS`.
  - Body params parsing: `allocationId` and `targetTaId`.
  - Delegation to `AllocationService.reassignAllocation`.

## Safety & Security

- **Authorization Gate**: Restricts reassignment strictly to professors and administrators (`Permission.ALLOCATE_SCRIPTS`).
- **Conflict Prevention**: Explicitly rejects requests if the target TA already has a pending allocation for that script/question.
- **Work Commencement Prevention (D2)**: Rejects reassignment of work that has already started or been graded by verifying that the allocation's status is strictly `PENDING` and no `Grade` exists matching the `answerScript` and `question`.
- **Rollback Guarantee**: In case of Mongoose pre-save integrity failures (e.g. mixed mode check), work commencement violations, or write conflicts, the transaction rolls back cleanly, keeping database allocations consistent and preventing dirty audit log writes.

## Verification

- Created a dedicated test file `src/__tests__/AllocationReassignment.test.ts` covering:
  - Rejection of unauthorized users (e.g. TAs, students).
  - Rejection if the target TA is not registered on the course.
  - Successful whole-script allocation reassignment.
  - Successful single-question allocation reassignment (asserting other questions for the same script remain untouched).
  - Cross-resource exam ID mismatch validation.
  - Conflict detection and transactional rollback.
  - Audit logging verification.
  - Rejection of non-PENDING allocation reassignments and verifying no database modifications or audit logs occur.
  - Rejection of reassignments when a Grade already exists (both question-wise and whole-script) and verifying no database modifications or audit logs occur.

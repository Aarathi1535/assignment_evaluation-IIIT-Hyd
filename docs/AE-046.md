# AE-046 — Render PDF Pages to Page Images

## Objective

Render each PDF page into a normalized page image and persist the corresponding page documents as the per-page ingestion assets.

This ticket replaces the current lightweight/stub implementation in `PageIngestionService.processPage` with real PDF page rendering and establishes the canonical normalized page-image representation that AE-048 will also use for direct image inputs.

## Architectural Decisions

### 1. PDF Renderer Selection: `pdfjs-dist` vs `pdf2pic`

**Decision**: Selected **`pdfjs-dist`** paired with **`sharp`** for image normalization.

**Rationale**:
- **Zero OS-level system dependencies**: `pdf2pic` requires external host binaries (`ghostscript` and `graphicsmagick`). In Linux CI (`ubuntu-latest`) or containerized deployments, `pdf2pic` requires `apt-get install ghostscript graphicsmagick` and relies on child process execution. `pdfjs-dist` is a self-contained JavaScript/WebAssembly library maintained by Mozilla that runs entirely within the Node.js runtime and installs cleanly via `npm ci`.
- **Cross-platform consistency**: `pdfjs-dist` guarantees identical PDF parsing behaviour across Linux, macOS, and Windows without binary path resolution issues.
- **Security**: Avoiding Ghostscript eliminates known PostScript interpreter vulnerability attack vectors when processing untrusted student/professor PDF uploads.
- **Performance & Normalization**: `sharp` handles native image resizing, bounding box calculations, DPI metadata embedding, and fast format conversion (PNG/WebP).

### 2. Canonical Normalized Page-Image Representation

The canonical normalized representation established here is shared with AE-048 (direct image inputs):
- **Output Format**: Lossless PNG (`image/png`) by default for crisp rubric and handwritten exam evaluation.
- **Resolution**: 150 target DPI (`DEFAULT_PAGE_RENDERING_CONFIG.targetDpi = 150`).
- **Maximum Long-Edge**: 2048px (`DEFAULT_PAGE_RENDERING_CONFIG.maxLongEdge = 2048`).
- **Hard Maximum Output Pixels**: 16,777,216 pixels ($4096 \times 4096$, 16.7 MP max ceiling) to bound memory consumption and prevent decompression/rendering resource exhaustion.
- **Contract Interface**: `RenderedPageImage` in `src/services/PageRenderer.ts` capturing `{ buffer, format, width, height, dpi, pageNumber, sizeBytes }`.

### 3. Injectable Renderer Abstraction

- Introduced `IPageRenderer` abstraction interface in `src/services/PageRenderer.ts`.
- `PageIngestionService` accepts an `IPageRenderer` dependency via constructor, setter (`setRenderer`), or per-call options.
- Removed production-only simulation flags (`simulatePageFailure`, `simulateHungPage`) and fabricated stack traces (`/app/renderer.ts:40`).
- Retained per-page `executeWithTimeout()` protection and sanitized failure reporting (`sanitizeFailureReason`).

## Scope

- Process each page of an uploaded PDF individually.
- Produce one normalized image asset per PDF page.
- Persist the corresponding page document for each extracted page.
- Replace the current lightweight page-extraction placeholder in `PageIngestionService.processPage`.
- Establish the canonical normalized page-image representation (format, dimensions/resolution and storage representation) for reuse by AE-048.
- Integrate with the existing ingestion pipeline without changing the upload contract.
- Preserve deterministic page numbering and existing idempotency behaviour.
- Use the actual PDF renderer's page count as the authoritative processing count, while retaining the existing upload-time page-count check as a cheap pre-flight guard.
- Bound rendering cost with a target DPI or maximum long-edge and a hard maximum output-pixel limit per page.
- Render pages sequentially or with bounded concurrency rather than unbounded `Promise.all`.
- Preserve the existing per-page `executeWithTimeout` protection.
- Keep rendering failures sanitized and remove fabricated/nonexistent stack traces.

## Acceptance Criteria

- A valid single-page PDF produces exactly one normalized stored page image and one corresponding `IngestionPage` document.
- A valid multi-page PDF produces one normalized stored page image and one corresponding `IngestionPage` document for every page reported by the actual renderer.
- Page numbering is deterministic and each page remains associated with the correct batch and source file.
- Reprocessing/retrying a page does not create duplicate page records or assets under the existing idempotency rules.
- The existing upload-time page-count check remains as a cheap pre-flight guard.
- The renderer's page count is authoritative for actual processing and `totalPages` is reconciled accordingly.
- Rendering cannot exceed the configured per-page output-pixel limit.
- Pages are rendered sequentially or with bounded concurrency.
- The existing per-page timeout remains effective.
- Production code does not expose `simulatePageFailure` or `simulateHungPage` test-only flags.
- Tests can substitute the renderer without modifying production behaviour.
- Rendering failures contain sanitized, meaningful error information and no fabricated stack frames.
- The selected rendering dependency installs and runs successfully in the Linux CI environment.
- ESLint, TypeScript, and relevant tests pass.

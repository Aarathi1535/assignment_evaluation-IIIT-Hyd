# AE-105: Performance Benchmark & Cache Feasibility Evaluation for Progress Aggregation

## Executive Summary

As part of **AE-105**, an empirical performance evaluation and benchmarking study was conducted on the progress aggregation pipeline (`AllocationService.getProgress()` and `GET /api/exams/[id]/progress`) across small, medium, large, and very large course workloads.

### Benchmark Key Findings:
* **Cold Read Latency**: $4.99\text{ ms} - 9.28\text{ ms}$ across all dataset sizes (200 to 5,000 allocations).
* **Warm Read Latency**: $3.44\text{ ms} - 8.74\text{ ms}$ across 20–30 consecutive executions.
* **Database Execution**: Single-stage index scan (`IXSCAN` on `{ exam: 1 }`), with server-side `$group` reducing thousands of allocations down to $\le 15$ documents in MongoDB memory before executing indexed `$lookup` for TA metadata.

### Architectural Decision (Decision Gate Outcome):
**Implementation Deferred (No Cache Introduced)**. The existing AE-098 aggregation pipeline executes in **sub-10ms** across all realistic workloads. Adding a distributed caching layer (e.g. Redis, TTL cache collections, or synchronized in-memory stores) would introduce significant architectural complexity, cross-instance invalidation overhead, and stale-data risks without providing meaningful latency improvements over the existing 4–8ms database read path.

## 3. Analysis of Why the Existing Aggregation is Fast

1. **Targeted Index Filtering**: The pipeline begins with `{ $match: { exam: examObjectId } }`. Because `AllocationSchema` contains an index on `{ exam: 1 }`, MongoDB performs an immediate index scan (`IXSCAN`), reading only the exact allocation documents belonging to the exam without scanning unrelated records.
2. **Server-Side Grouping**: The `$group` stage calculates `total` and `graded` counts directly in MongoDB engine memory. It reduces thousands of allocation documents down to only $N$ documents, where $N$ is the number of TAs on the course (typically 5 to 20 rows).
3. **Bounded Primary Key Lookups**: The `$lookup` stage joins against `User` (`_id`) for only those 5 to 20 TA summary records.
4. **Zero Document Over-Fetching**: Node.js receives only the aggregated 5 to 20 TA summary objects; zero raw allocation records are pulled over the wire into application process memory.

## 4. Why Introducing a Cache Is Unjustified

1. **Marginal Latency Gains vs. Cache Overhead**:
   - Current database aggregation latency is **3.4ms to 8.7ms**.
   - Querying an external shared cache (such as Redis or a MongoDB cache collection) across a network socket takes **1ms to 3ms**.
   - The maximum possible latency reduction is $\approx 3-5\text{ ms}$, which is imperceptible to human users and unnecessary for professor-facing dashboards.
2. **Multi-Instance Container Safety**:
   - The production target is a container deployment across multiple instances.
   - An in-memory cache (e.g. `node-cache`, `lru-cache`, or JavaScript `Map`) is strictly unsafe across containers because completions on Container $A$ cannot synchronously invalidate memory on Container $B$.
3. **Invalidation & Staleness Hazards**:
   - Adding a shared caching layer introduces cache synchronization failure modes, TTL staleness windows, cache stampede risks, and potential inconsistencies during rapid completion transactions (`AllocationService.markCompleted`).
4. **Synergy with Live Progress (AE-102)**:
   - AE-102 already provides real-time Server-Sent Events (SSE) pushed directly on allocation completion via MongoDB Change Streams. Instructors observing real-time progress receive live streaming updates without high-frequency polling.

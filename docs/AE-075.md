# AE-075 — Immutable Seal of Approved Assembly State

This document explains the design, implementation, and lifecycle of the **Ingestion Assembly Seal** introduced in AE-075.

---

## 1. Overview & Mentor-Approved Reframe

Under AE-043, the **original uploaded file bytes** are already cryptographically sealed and protected by `ImmutableStorageService` and `hmacStorage` at the moment of upload. This guarantees that raw submissions cannot be altered or overwritten.

**AE-075 does not duplicate original-byte sealing. Instead, it seals the approved arrangement of those pages into scripts and their associated student identification bindings.**

Once a reviewer (Professor or Admin) clicks **Approve Ingestion** (AE-074):
1. The logical structure (page arrangement, script splits, student IDs) is serialized deterministically.
2. A cryptographic HMAC seal of this serialization is generated.
3. The seal and its key configuration are stored on the `Exam` model.
4. Any subsequent out-of-band tampering or script re-assignment is immediately caught during integrity verification.

---

## 2. Ingestion Assembly vs. Original Files

The distinction between the two sealing layers is as follows:

| Layer | Protected Entity | When Generated | Verification Trigger |
| :--- | :--- | :--- | :--- |
| **AE-043 Original Seal** | Uploaded bytes (`PDF`/`Image`) | Upload / batch creation | Prior to pipeline processing |
| **AE-075 Assembly Seal** | Logical script mapping, student binding, & page order | Ingestion approval | Manual check / prior to allocation |

---

## 3. Canonical Serialization & Deterministic Ordering

To ensure that the cryptographic signature is stable and reproducible, the assembly state is serialized into a canonical representation. 

To prevent differences in database query return order, we enforce the following sorting:
- **Scripts**: Sorted lexicographically by their `_id` hex string.
- **Pages**: Sorted numerically by their `pageNumber` (which preserves explicit page order).

### Included Fields
The serialized payload contains only deliberate, non-regenerable fields:
- **Exam ID**
- **AnswerScript fields**:
  - `scriptId` (Mongoose Hex ID)
  - `student` (Assigned User ID or `"null"`)
  - `identificationSource` (`QR` \| `OMR` \| `OPERATOR` \| `OCR` \| `null`)
  - Review flags: `needsManualId` (boolean), `manualIdReason` (string or null), `hasIdentificationConflict` (boolean)
- **IngestionPage fields** (listed under each script in order):
  - `pageId` (Mongoose Hex ID)
  - Original source/storage identity: `batchId` (string), `fileId` (string), `pageNumber` (number)
  - Review flags: `nearBlank` (boolean), `isDuplicate` (boolean), `duplicateOf` (Mongoose Page ID or null)

> [!NOTE]
> We explicitly exclude derived previews, thumbnails, and other regenerable assets (like `thumbnailKey`, `enhancementParams`) from the canonical seal payload.

### Example Canonical Layout:
```
exam:65e123...
script:65e456...|student:65e789...|source:QR|needsManualId:false|manualIdReason:null|hasConflict:false
  page:65eaaa...|batch:b-1|file:f-1|num:1|nearBlank:false|isDuplicate:false|duplicateOf:null
  page:65ebbb...|batch:b-1|file:f-1|num:2|nearBlank:false|isDuplicate:false|duplicateOf:null
```

---

## 4. Persisted Seal Metadata

The seal metadata is stored directly on the `Exam` model:
- `assemblySeal`: Cryptographic HMAC (sha256 hex string).
- `assemblySealKeyId`: Key ID used to generate it (e.g. `v1`). Supports key rotation.
- `assemblySealAt`: The timestamp when the seal was generated.
- `assemblySealBy`: Reference to the `User` who approved ingestion and sealed it.

---

## 5. Ingestion Seal Lifecycle

```
                     ┌───────────────────────────────────────────────┐
                     │                                               │
                     ▼                                               │
           PENDING_REVIEW  ──[approve]──►  APPROVED (with seal)      │
                 ▲                            │                      │
                 │                            │                      │
                 └──────────[revoke]──────────┘                      │
                 │                                                   │
                 └──────────[new successful batch]─────────────────►─┘
```

1. **Approval**: Generating a seal is mandatory. If seal creation fails (e.g. key missing), the approval fails cleanly.
2. **Revocation**: Reverts status to `PENDING_REVIEW` and sets all seal fields (`assemblySeal`, `assemblySealKeyId`, etc.) to `null`.
3. **New Batch**: When a new successful batch is uploaded, the status is automatically reset to `PENDING_REVIEW` and seal fields are cleared.
4. **Re-approval**: Regenerates a fresh canonical seal based on the updated script configuration.

---

## 6. Verification Flow

An authorized reviewer triggers verification through the API or frontend. The system:
1. Loads the stored seal metadata (`assemblySeal`, `assemblySealKeyId`, `assemblySealAt`, `assemblySealBy`).
2. Reconstructs the `IBindingMetadata` (where `batchId` = `examId`, `uploader` = `assemblySealBy`, `timestamp` = `assemblySealAt.getTime()`).
3. Computes the canonical assembly string of the current state.
4. Calls `verifyHmacSeal` to compute the expected HMAC and perform a timing-attack safe comparison.
5. Returns a structured result:
   - `valid: true, status: 'INTACT'`
   - `valid: false, status: 'MISMATCH'` (if pages/bindings have tampered/changed)
   - `valid: false, status: 'ERROR'` (if historical HMAC key is missing)

---

## 7. Auditing & Security

All actions are recorded in the system's `AuditLog` collection:
- `INGESTION_APPROVED`: Records the seal details and keys used.
- `INGESTION_ASSEMBLY_VERIFIED`: Records the outcome (`SUCCESS` / `FAILURE`), timestamp, status (`INTACT` \| `MISMATCH` \| `ERROR`), and reviewer context.

To preserve security, **no HMAC secret keys** are written to any audit logs.

---

## 8. API & UI

### Verification Endpoint
- `POST` `/api/exams/[id]/verify-assembly`
- Requires `Permission.APPROVE_INGESTION`.
- Scope-checked: Professor can only verify exams they own.

### Frontend Panel
The status card in the exam details view shows the seal state. Clicking **Verify Integrity** triggers the verification. In case of a mismatch, a prominent warning status is displayed.

# AE-097 — TA Work-Queue Sorting

## Objective
Implement oldest-first queue sorting for the TA grading work queue. The allocations returned to the authenticated TA must be sorted oldest first by default. If a TA requests sorting explicitly (via query parameters), the backend must support oldest-first ordering, but reject any other sorting schemes (like difficulty/complexity sorting) with HTTP 400 Bad Request.

## Implementation Details

### API Endpoint: `GET /api/allocations`
- **TA Restriction**: Enforces permissions check at the route level via `requirePermission(Permission.VIEW_ASSIGNED_SCRIPTS)`. The query isolates allocations strictly matching `ta: auth.user.id`.
- **Default Order**: The allocations are returned sorted oldest first (by `createdAt` ascending) by default.
- **Explicit Sorting**: Supports `sort` or `sortBy` query parameters.
  - Valid sort parameter values: `'oldest'`, `'oldest-first'`, or `'createdAt'`.
  - These values sort the allocations by `createdAt` in ascending order.
- **Invalid Sort Rejection**: If an invalid sort value (e.g. `'newest'`, or `'difficulty'`) is passed, the endpoint returns an HTTP 400 Bad Request response with a validation error message.
- **Filters Preservation**: Supports existing filtering parameters such as `examId` and `status` seamlessly, matching the query criteria prior to sorting.

## Deferral of Difficulty-Based Sorting (AE-097b)

> [!IMPORTANT]
> **Deferred Work (AE-097b)**:
> No difficulty or complexity metrics (such as page count, file size, question count, marks, etc.) currently exist in the database schemas or models.
> Therefore, difficulty-based sorting has been deferred to future ticket `AE-097b`.
> The backend explicitly rejects any sort parameter values that refer to difficulty, complexity, or other unsupported attributes with an HTTP 400 Bad Request error. We do not invent custom proxy metrics (like estimating difficulty from page count) to avoid introducing false assumptions.

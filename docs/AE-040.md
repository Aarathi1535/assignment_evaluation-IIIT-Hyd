# AE-040 – Rubric Attachment, Versioning & Locking

## Objective

Attach grading rubrics to exams while introducing version metadata and preventing rubric modification once grading has started.

This ensures grading consistency by making rubrics immutable after evaluation begins.

---

## Functional Requirements

### Exam Association

- Each exam references a single active rubric.
- Duplicate active rubrics for the same exam are prevented.

---

### Versioning

- New rubrics are created with version 1.
- Version metadata is stored for future extensibility.

---

### Locking

A rubric becomes locked when grading has started for that rubric.

Once locked:

- Rubrics cannot be modified.
- Update requests are rejected.
- The API reports the rubric as locked.

---

### Read-only User Interface

When a rubric is locked:

- Display a warning banner.
- Disable all editable fields.
- Hide editing actions.
- Prevent saving changes.

---

## Acceptance Criteria

- Rubrics are attached to exams during creation.
- Only one active rubric exists per exam.
- Version defaults to 1.
- Locked rubrics cannot be modified.
- Read-only mode is displayed correctly.
- Existing authorization behaviour is preserved.

---

---

## Security Notes

- Lock enforcement is performed in the service layer rather than relying on the frontend.
- The frontend provides usability by disabling editing controls, while the backend guarantees immutability by rejecting update requests.

## Rubric Visibility

Students enrolled in an exam are permitted to view the associated grading rubric. This is an intentional design decision to provide grading transparency and communicate the evaluation criteria before or during assessment.

Rubric modification remains restricted to authorized staff (Professor and Admin). Once grading has started, the rubric becomes immutable and is presented in read-only mode to all users with access.

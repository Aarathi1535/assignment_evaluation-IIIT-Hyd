# AE-079 — Ingestion Performance Check vs 5000 Pages/Hour

## Objective
The goal of this ticket is to measure the page ingestion pipeline throughput against the target of **5000 pages/hour**, isolate per-stage bottlenecks, and evaluate the current job worker processing model to guide optimizations in AE-080.

---

## Test Environment
*   **Operating System**: Windows (Local Dev Environment)
*   **CPU**: Multicore Intel/AMD CPU (up to 12 threads active)
*   **Storage**: Local SSD (simulating immutable and derived object storage via disk writes)
*   **Database**: In-memory MongoDB (Mongoose)
*   **Runtime**: Node.js with Vitest test execution runner

---

## Measurement Method
*   **Fixture Used**: Reusable 100-page mixed-input fixture from AE-078.
*   **Mixed-Input Composition**:
    *   1 x 95-page PDF document (`alice_exam_95pg.pdf`)
    *   5 x 1-page PNG standalone images (`bob_omr_1pg.png`, `charlie_qr_omr_1pg.png`, `unknown_student_1pg.png`, `nocode_blank_1pg.png`, `multiple_qr_1pg.png`)
*   **Timing Mechanism**: Timing wrapper classes and Mongoose function decorators using Node.js high-resolution `performance.now()`.
*   **Throughput Calculation**:
    $$\text{Estimated Pages/Hour} = \frac{\text{Total Pages}}{\text{Total Duration (Hours)}} = \frac{100 \text{ pages}}{\text{Total Duration (ms)}} \times 3,600,000$$

---

## Results
*   **Total Duration**: 52700.13 ms (52.70 seconds)
*   **Pages Processed**: 100 pages
*   **Average Time Per Page**: 527.00 ms/page
*   **Estimated Throughput**: **6831.10 pages/hour**
*   **Comparison**: **ABOVE TARGET** (The estimated throughput of 6831.10 pages/hour exceeds the target of 5000 pages/hour on the local dev environment).

---

The table below lists the measured durations for each distinct stage in the ingestion path:

| Ingestion Stage | Measured Time (ms) | Percentage of Total Time (%) | Status / Notes |
| :--- | :--- | :--- | :--- |
| **Render / Extraction** | 12166.48 ms | 23.09% | Real PDF rendering using `pdfjs-dist` |
| **Image Enhancement** | 0.27 ms | < 0.01% | Mocked (No-Op) |

*Note: The "Other/Unclassified" category covers disk write latencies (derived/immutable storage writes on SSD) and internal execution overhead.*

---

## Bottlenecks
Based on the per-stage measurements:
1.  **Render / PDF Extraction**: Takes **12166.48 ms** (~23% of total time). This is the slowest isolated CPU-bound stage. Rendering pages from legacy PDFs using `pdfjs-dist` in Node.js requires substantial CPU execution.
2.  **QR Code Detection (Cover Sheets)**: Takes **3552.91 ms** (~6.7% of total time). Scanning the sub-regions (quadrants and halves) using ZXing adds notable per-page processing overhead on cover sheets.
3.  **File System I/O & Storage Overhead**: Unclassified overhead (largely disk writes for writing original/derived pages and thumbnails) represents the largest portion of the pipeline (~67%). Writing files sequentially to storage adds significant block latency.

---

## Worker Concurrency Finding
The current implementation of the job processing queue is **effectively single-threaded at the job-processing level**:
*   The worker processes exactly one ingestion job at a time sequentially.
*   While a single-threaded queue ensures absolute safety and avoids database race conditions, it acts as a primary scalability constraint.
*   Introducing multi-job concurrent processing (e.g. processing multiple pages or multiple batches in parallel) would provide a orders-of-magnitude greater throughput increase than micro-optimizing CPU-bound renderer calls.

---

## Interpretation and Limitations
> [!IMPORTANT]
> **The sample extrapolation is not proof of sustained production throughput.**

The 100-page benchmark run on a development/test environment does not reflect:
1.  **Sustained Operation**: Heat throttling, memory leaks, or GC pauses over one-hour continuous workloads.
2.  **Production Hardware**: Differences in CPU core speeds, available RAM, and container limits in a cloud environment (e.g., Kubernetes limits vs. dev laptops).
3.  **Network/Storage Latency**: The dev environment uses zero-latency local disk writes. Production environments use network storage (e.g., AWS S3 or Google Cloud Storage) which adds 50ms–200ms per file upload.
4.  **Concurrent Workloads**: No simultaneous workloads were running during this test. In production, multiple parallel users and batch jobs will contend for Mongo and storage resources.

---

## Follow-up Recommendations for AE-080
1.  **Target PDF Rendering Optimization**: Explore pre-compiling or caching PDF streams, or evaluate faster native rendering alternatives.
2.  **Storage / IO Buffering**: Parallelize derived storage write operations (derived PNGs, thumbnails) instead of awaiting each file save sequentially.
3.  **Batch/Worker Concurrency**: Implement parallel workers or page-level thread pool execution to scale throughput dynamically.

# AE-043 – Immutable HMAC Storage

## Objective

Store uploaded original files as tamper-evident, application-layer immutable originals using HMAC-sealed storage.

## Immutability & Scope Clarifications

- **Application-Layer Immutability & Cryptographic Tamper-Evidence**: AE-043 provides application-layer immutability and cryptographic HMAC tamper-evidence for original uploaded assets and binding metadata.
- **No Storage-Level WORM**: It is NOT storage-level WORM (Write Once, Read Many), hardware/cloud object-lock, or filesystem-level retention enforcement.
- **Retention & PII Policies Deferred**: Long-term retention, scheduled pruning, and deletion policies for student answer scripts and associated personally identifiable information (PII) are deferred and out of scope for this ticket.

## Acceptance Criteria

- [ ] Uploaded originals are written through the immutable storage layer.
- [ ] The HMAC key is loaded from environment/secret configuration using the same secure configuration pattern as `NEXTAUTH_SECRET`.
- [ ] The application fails to start if the HMAC key is missing.
- [ ] The HMAC key is never committed to the repository or stored in source code.
- [ ] Each seal stores a key ID so previously stored originals remain verifiable after key rotation.
- [ ] The HMAC covers both file content and binding metadata: batch ID, page/sequence number, uploader, and timestamp.
- [ ] Stored originals cannot be modified through the application storage interface.
- [ ] Integrity information is persisted and can be verified using the corresponding key ID.
- [ ] Integrity verification is implemented as an internal utility rather than a public API endpoint.
- [ ] Original storage access is restricted to authorized users and enforced through repository-layer ownership checks.
- [ ] Storage operations generate the required audit information with appropriate `SUCCESS`/`FAILURE` outcomes.
- [ ] Partial failures are handled safely: file write → HMAC seal → database record persistence, with cleanup or reconciliation for failed later stages.
- [ ] Existing authentication and authorization behaviour is preserved where applicable.

## Validation

- [ ] Test successful immutable original storage.
- [ ] Test HMAC seal generation.
- [ ] Test application startup/configuration failure when the HMAC secret is missing.
- [ ] Test that the HMAC includes the required binding metadata.
- [ ] Test key ID persistence and verification.
- [ ] Test integrity verification with valid content and metadata.
- [ ] Test integrity verification failure after content modification.
- [ ] Test integrity verification failure after metadata modification or record swapping.
- [ ] Test application-layer modification/write attempts are rejected.
- [ ] Test repository-level authorization for reading stored originals.
- [ ] Test successful and failed storage audit events.
- [ ] Test cleanup/reconciliation behaviour for partial storage failures.
- [ ] ESLint passes.
- [ ] TypeScript passes.
- [ ] All tests pass.

## Out of Scope

- Storage-level WORM enforcement such as object-lock, retention policies, or filesystem permissions. AE-043 provides application-layer immutability plus cryptographic HMAC tamper-evidence.
- Public integrity-verification API.
- Key-management infrastructure or external KMS implementation.
- Retention/deletion policy for student answer-script data and associated PII (deferred/out of scope).
- Batch upload endpoint implementation (AE-042).
- Background ingestion job execution (AE-044).
- Ingestion status API implementation (AE-045).

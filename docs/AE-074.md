# AE-074 — Reviewer "Approve Ingestion" Step per Exam

## Objective

Implement a persisted ingestion approval gate for exams. After ingestion is
complete a reviewer (professor or admin) must explicitly approve the assembly
before grading or allocation can proceed. The canonical approval state is stored
on the `Exam` model in MongoDB and is the single source of truth.

---

## Approval State Model

### Location

New fields on `Exam` (src/models/Exam.ts). Approval is per exam, not per batch.

### States

| State            | Meaning                                          |
|------------------|--------------------------------------------------|
| `PENDING_REVIEW` | Default. Ingestion awaits reviewer sign-off.     |
| `APPROVED`       | Reviewer has confirmed the ingestion assembly.   |

### Stored Fields

| Field                    | Type        | Description                               |
|--------------------------|-------------|-------------------------------------------|
| `ingestionApprovalStatus`| enum string | `PENDING_REVIEW` or `APPROVED`            |
| `approvedBy`             | ObjectId?   | ID of the user who last approved          |
| `approvedAt`             | Date?       | UTC timestamp of approval                 |

All new exams default to `PENDING_REVIEW`. Existing documents without the field
are treated as `PENDING_REVIEW` by all application code.

---

## State Transitions

```
                    ┌──────────────────────────────────────────────────┐
                    │                                                  │
                    ▼                                                  │
          PENDING_REVIEW ──[approve]──► APPROVED                      │
                ▲                           │                         │
                │                           │                         │
                └──────────[revoke]─────────┘                         │
                │                                                     │
                └──────────[new successful batch]──────────────────►──┘
                           (only if was APPROVED)
```

- `approve`: `PENDING_REVIEW → APPROVED`
- `revoke`: `APPROVED → PENDING_REVIEW`, clears `approvedBy`/`approvedAt`
- `new batch`: If exam was `APPROVED`, resets to `PENDING_REVIEW` automatically

## API Endpoints

### POST /api/exams/[id]/approve-ingestion

Transitions the exam from `PENDING_REVIEW` to `APPROVED`.

**Permission:** `APPROVE_INGESTION` (Professor, Admin)

**Responses:**

| Code | Condition                                            |
|------|------------------------------------------------------|
| 200  | Successfully approved                                |
| 400  | Invalid exam ID format                               |
| 403  | Caller lacks `APPROVE_INGESTION` permission          |
| 404  | Exam not found or caller does not own it             |
| 409  | Exam is already in `APPROVED` state                  |

---

### POST /api/exams/[id]/revoke-ingestion

Transitions the exam from `APPROVED` to `PENDING_REVIEW`.

**Permission:** `APPROVE_INGESTION` (Professor, Admin)

**Responses:**

| Code | Condition                                            |
|------|------------------------------------------------------|
| 200  | Successfully revoked                                 |
| 400  | Invalid exam ID format                               |
| 403  | Caller lacks `APPROVE_INGESTION` permission          |
| 404  | Exam not found or caller does not own it             |
| 409  | Exam is already in `PENDING_REVIEW` state            |

---

### POST /api/exams/[id]/allocate (Allocation Gate)

Checks whether ingestion is approved before allowing grading or allocation.
Returns `403` with a clear message if the exam is not yet approved.

**Permission:** `ALLOCATE_SCRIPTS`

> Full allocation business logic is implemented in future tickets. This endpoint
> establishes the gate required by AE-074.

## Batch Invalidation

When a new batch is successfully created (`BatchService.createBatch` succeeds)
for an exam-linked batch:

1. `IngestionApprovalService.resetToReview(examId, ...)` is called.
2. If the exam was `APPROVED`, it is atomically reset to `PENDING_REVIEW`.
3. `approvedBy` and `approvedAt` are cleared.
4. An audit record is written with action `INGESTION_APPROVAL_RESET_BY_NEW_BATCH`.

**No-op if:** Exam is already `PENDING_REVIEW` (avoids redundant DB writes).
**Non-fatal:** If the reset fails, the batch creation is not rolled back. The
audit trail captures the failure.

## Correction Freeze (AE-064 integration)

Once ingestion is `APPROVED`, all script composition and page ordering mutations
are blocked:

| Operation  | Method                          | Blocked Response |
|------------|---------------------------------|------------------|
| Remap      | `CorrectionService.remapPage`   | HTTP 409         |
| Merge      | `CorrectionService.mergeScripts`| HTTP 409         |
| Split      | `CorrectionService.splitScript` | HTTP 409         |
| Reorder    | `CorrectionService.reorderPages`| HTTP 409         |

The 409 message directs the reviewer to revoke approval first.

The check is implemented as a private `assertIngestionNotApproved` helper in
`CorrectionService`, called after the batch ownership check in each method.

## Authorization

| Action         | Required Permission   | Granted To              |
|----------------|-----------------------|-------------------------|
| Approve        | `APPROVE_INGESTION`   | PROFESSOR, ADMIN        |
| Revoke         | `APPROVE_INGESTION`   | PROFESSOR, ADMIN        |
| Allocate gate  | `ALLOCATE_SCRIPTS`    | PROFESSOR, ADMIN, TA    |

Professor scope rules from `ExamRepository.buildExamQuery` are enforced:
professors can only approve/revoke exams they own.

## Auditing

Every state transition creates an `AuditLog` record:

| Action                                  | When                              |
|-----------------------------------------|-----------------------------------|
| `INGESTION_APPROVED`                    | Exam transitions to APPROVED      |
| `INGESTION_APPROVAL_REVOKED`            | Exam reverted to PENDING_REVIEW   |
| `INGESTION_APPROVAL_RESET_BY_NEW_BATCH` | New batch auto-resets approval    |

Audit fields:
- `user` — acting user ID
- `action` — action enum above
- `outcome` — `SUCCESS`
- `entityId` — exam `_id`
- `entityType` — `Exam`
- `details` — previous/new state, timestamps, reason
- `ipAddress` — from request headers

## Frontend

### `IngestionApprovalPanel` component

Located at `src/components/ui/IngestionApprovalPanel.tsx`.

- Displays current status badge (`PENDING_REVIEW` / `APPROVED`).
- Shows approval timestamp when approved.
- Shows an amber warning note when pending review.
- **Approve Ingestion** button (shown when PENDING_REVIEW).
- **Revoke Approval** button (shown when APPROVED).
- After every mutation, refreshes canonical state from `GET /api/exams/[id]`.
- No frontend-only approval state — always driven by server state.

### Integration in BatchStatusView

The panel is rendered automatically in `BatchStatusView` when:
- Ingestion status is `done`
- The batch is linked to an exam (`examId` is set)

The ingest status API (`GET /api/ingest/[id]`) now includes `examId`,
`ingestionApprovalStatus`, `approvedBy`, and `approvedAt` in its response.

## Service Architecture

```
IngestionApprovalService
  ├── approveIngestion(examId, context)    — PENDING_REVIEW → APPROVED
  ├── revokeApproval(examId, context)      — APPROVED → PENDING_REVIEW
  ├── requireApproved(examId)              — Gate check (throws 403)
  └── resetToReview(examId, context)       — Auto-reset on new batch
```

Used by:
- API routes (approve-ingestion, revoke-ingestion, allocate)
- `BatchService.createBatch` (calls `resetToReview`)
- `CorrectionService.assertIngestionNotApproved` (calls `Exam.findOne`)

# AE-078 — End-to-End Ingestion QA with 100-Page Mixed Fixture

## Objective

The objective of AE-078 is to establish and verify an end-to-end ingestion QA test (`src/__tests__/Ingestion100PageE2E.test.ts`) that exercises the complete page ingestion, page rendering, student identification (QR code and OMR bubble matching), and answer script assembly pipeline using a deterministic mixed-input fixture totaling exactly 100 pages. 

This test guarantees that the ingestion worker, storage layers, and roster mapping service cooperate correctly under high-load conditions while maintaining page order, file sequence, and boundary-preserving script splitting.

## Fixture Composition

The deterministic fixture generated programmatically during the test consists of the following components:

*   **Multi-Page PDFs**: 1 file
    *   `alice_exam_95pg.pdf` — A 95-page programmatically generated PDF. Page 1 is intercepted by a custom rendering hook to output a valid QR code raster image containing `ROLL-ALICE`, while pages 2–95 are rendered normally via the legacy `pdfjs-dist` integration.
*   **Single-Page Images**: 5 files
    *   `bob_omr_1pg.png` — A 1-page PNG image containing filled OMR bubble marks corresponding to Bob's mapped ID `10`.
    *   `charlie_qr_omr_1pg.png` — A 1-page PNG image containing both a QR code (`ROLL-CHARLIE`) and OMR bubbles (`01`).
    *   `unknown_student_1pg.png` — A 1-page PNG image containing a QR code for a student not present in the roster (`ROLL-UNKNOWN`).
    *   `nocode_blank_1pg.png` — A 1-page blank PNG image containing no QR or OMR codes.
    *   `multiple_qr_1pg.png` — A 1-page PNG image containing multiple conflicting QR codes.
*   **Total Pages**: 100 pages
*   **Cover Sheets**: 6 cover sheets (page 1 of each of the 6 files).
*   **Expected Scripts**: 6 logical scripts (one script per uploaded file).
*   **Cross-File Boundaries**: Checked but not merged. Both cover-sheet splitting and fixed-page splitting strategies in the repository's active codebase explicitly close the current script range when the `fileIndex` changes. The test verifies that file boundaries act as absolute boundaries and script pages do not bleed across different files.

## Pipeline Coverage

The integration test runs the actual production pipeline components, executing the following stages:

*   **Ingestion Job Processing**: *Real*. The batch is created via `BatchService.createBatch` and processed by calling `IngestionWorker.processNextJob()`.
*   **Page Rendering / Extraction**: *Real*. PDF page extraction and rendering are executed using `DefaultPdfRenderer` and standalone images are normalized via `DefaultImageRenderer`.
*   **Enhancement**: *Mocked / No-op*. Ingestion100PageE2E.test.ts mocks ImageEnhancer as a no-op returning the buffer unchanged. The enhancement parameters are populated, but the enhancement itself is not truly exercised.
*   **Thumbnail Generation**: *Real*. Deterministic page thumbnails are generated via the canvas resizing library.
*   **QR Detection**: *Real*. Scanned cover page PNG buffers are analyzed using the native `@zxing/library` implementation.
*   **OMR Processing**: *Real*. The OMR fallback bubble reader (`OMRReader`) runs on the cover pages, matching against coordinates configured in the exam's `omrTemplate`.
*   **Page Persistence**: *Real*. Ingestion pages are persisted into MongoDB Memory Server as `IngestionPage` documents, preserving fields like `fileIndex`, `pageNumber`, `isCoverPage`, and identification metadata.
*   **Script Assembly**: *Real*. `StudentRosterMappingService` groups the pages, applies the exam's cover splitting strategy, and creates `AnswerScript` records.
*   **Student Identification**: *Real*. Identifies students from course enrollment and mappings by resolving IDs from both QR and OMR fallback, using the correct precedence rules.

## Assertions

The test suite validates the following system behaviors:

1.  **Page Counts**: Verifies that exactly 100 pages are processed and saved in the database under `processedPages = 100` and `failedPages = 0`.
2.  **Script Counts**: Verifies that exactly 6 scripts are created.
3.  **Page Ordering**: Verifies that pages within multi-page documents (`fileIndex = 0`) are sorted and stored sequentially (`pageNumber` 1 through 95).
4.  **File Indexing**: Verifies that files are assigned sequential zero-based indices (0 to 5) matching their upload receipt order.
5.  **Cover-Sheet/Script Boundaries**: Verifies that page 1 of each file is flagged with `isCoverPage = true`.
6.  **Student Binding**:
    *   **Alice** resolves to her database student record using the QR code payload (`ROLL-ALICE`).
    *   **Bob** resolves to his database student record using OMR bubbles (`10`) since no QR is present.
    *   **Charlie** contains both QR (`ROLL-CHARLIE`) and OMR bubbles (`01`). The script correctly resolves to Charlie using the QR identifier, verifying **QR code precedence** over OMR fallback.
7.  **Manual ID Reasons**:
    *   **Unknown student** QR code results in `needsManualId = true` and `manualIdReason = NOT_IN_ROSTER`.
    *   **Blank page** results in `needsManualId = true` and `manualIdReason = NO_CODE_FOUND`.
    *   **Multiple QR codes** results in `needsManualId = true` and `manualIdReason = MULTIPLE_CODES`.
8.  **Cross-File Behavior**: Verifies that all 6 scripts start at `startPageNumber: 1` within their respective `fileIndex` boundaries.

## Timing Metrics

The test measures processing duration by taking high-resolution timestamps before and after job execution:

*   **Total Duration**: The overall milliseconds elapsed during `worker.processNextJob()`.
*   **Processed Pages**: 100 pages.
*   **Average Milliseconds Per Page**: Total Duration / 100.

*Note: These metrics serve as a representative QA checkpoint and a baseline for performance regressions. They are subject to CPU availability in different environments (like local laptops or shared CI agents) and do not represent sustained production throughput.*

## Known Limitations

*   **Mocking PDF Page 1 QR Content**: To avoid committing binary PDF fixtures containing pre-rendered barcode data, we programmatically generate a minimal vector PDF. Since the basic PDF stream lacks barcode marks, we hook into `DefaultPdfRenderer.renderPage` specifically for Page 1 of the PDF to return a raster PNG with Alice's QR code. Pages 2–95 are rendered using the legacy PDF renderer. This ensures the PDF processing workflow is fully verified without requiring static binary storage.
*   **Cross-File Script Splitting**: By repository design, the splitting strategies explicitly terminate script assembly at file boundaries. Therefore, the test asserts that files are split into distinct scripts and cannot be combined across files.

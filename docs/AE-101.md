# AE-101 — Week-5 Demo: Allocation and TA Work Queue Workflow

This document provides the canonical demo script and operational runbook for the **Week-5 Allocation & Work-Queue Milestone**. It demonstrates the end-to-end flow from professor-configured script allocation to TA grading queue management, status transitions, and progress aggregation.

---

## 1. Objective & Scope

The Week-5 demo presents the completed allocation subsystem:
* Side-effect-free allocation preview and rule-based execution (`EQUAL`, `QUESTION`, `RANDOM`).
* TA work queue access, strict ownership scoping, and blind-grading student PII protection.
* Deterministic oldest-first queue ordering and pagination.
* Atomic state transitions: `PENDING` $\leftrightarrow$ `IN_PROGRESS` $\rightarrow$ `COMPLETED`.
* Backup operator override release by Professors/Admins.
* Real-time server-side progress aggregation showing completed vs total counts.

---

## 2. Step-by-Step Demo Execution Sequence

### Step 1: Professor Previews Allocation
* **Actor**: Professor (`Permission.ALLOCATE_SCRIPTS`)
* **Action**: Calls `POST /api/exams/[id]/allocate/preview` to inspect distribution counts before writing to database.
* **Request**:
  ```http
  POST /api/exams/60c72b2f9b1d8a001f8e1235/allocate/preview
  Content-Type: application/json

  {
    "rule": "EQUAL",
    "taIds": [
      "60c72b2f9b1d8a001f8e1001",
      "60c72b2f9b1d8a001f8e1002"
    ]
  }
  ```
* **Expected Response (200 OK)**:
  ```json
  {
    "success": true,
    "message": "Allocation preview generated successfully",
    "data": {
      "allocationCounts": {
        "60c72b2f9b1d8a001f8e1001": 10,
        "60c72b2f9b1d8a001f8e1002": 10
      },
      "totalEligibleScripts": 20,
      "totalExcludedScripts": 2,
      "excludedCountsByReason": {
        "NEEDS_MANUAL_ID": 1,
        "NEAR_BLANK": 1
      }
    }
  }
  ```

### Step 5: Verify Blind-Grading Privacy Protection
* **Behavior Verified**:
  * For blind-grading enabled exams, `student`, `qrStudentId`, `omrStudentId`, and `candidateStudentId` fields are strictly excluded from the payload.
  * TAs grade scripts referencing only `anonymousId` and `scriptReference`.

---

### Step 6: TA Claims a Script (`PENDING` $\rightarrow$ `IN_PROGRESS`)
* **Actor**: Teaching Assistant `ta1` (`Permission.GRADE_SCRIPT`)
* **Action**: Calls `POST /api/allocations/60c72b2f9b1d8a001f8e1301/claim`.
* **Expected Response (200 OK)**:
  ```json
  {
    "success": true,
    "message": "Allocation claimed successfully",
    "data": {
      "_id": "60c72b2f9b1d8a001f8e1301",
      "status": "IN_PROGRESS",
      "ta": "60c72b2f9b1d8a001f8e1001"
    }
  }
  ```
* **Audit**: Emits `ALLOCATION_CLAIM` audit log.

---

### Step 7: TA Releases a Script (`IN_PROGRESS` $\rightarrow$ `PENDING`)
* **Actor**: Teaching Assistant `ta1` (`Permission.GRADE_SCRIPT`)
* **Action**: Calls `POST /api/allocations/60c72b2f9b1d8a001f8e1301/release`.
* **Expected Response (200 OK)**:
  ```json
  {
    "success": true,
    "message": "Allocation released successfully",
    "data": {
      "_id": "60c72b2f9b1d8a001f8e1301",
      "status": "PENDING",
      "ta": "60c72b2f9b1d8a001f8e1001"
    }
  }
  ```
* **Audit**: Emits `ALLOCATION_RELEASE` audit log.

---

### Step 8: Professor Override Release
* **Actor**: Professor (`Permission.ALLOCATE_SCRIPTS`)
* **Precondition**: TA claims allocation (`status: IN_PROGRESS`).
* **Action**: Professor calls `POST /api/allocations/60c72b2f9b1d8a001f8e1301/release`.
* **Expected Result**: Successfully resets status to `PENDING`, emitting an `ALLOCATION_RELEASE` audit log with `isOverride: true`.

---

### Step 9: Complete Allocation via `AllocationService.markCompleted()`
* **Actor**: System / TA Completion Flow
* **Action**: Invokes `AllocationService.markCompleted(allocationId, actor)`.
* **Transition**: Atomically updates `IN_PROGRESS` $\rightarrow$ `COMPLETED`.
* **Idempotency**: Repeated calls return `409 Conflict` and prevent double-counting.
* **Audit**: Emits `ALLOCATION_COMPLETE` audit log.

## 3. Explicitly Deferred Functionality

| Feature | Status / Milestone | Current System Behavior |
| :--- | :--- | :--- |
| **Difficulty-Based Sorting** | Deferred to **AE-097b** | Sort parameter `sort=difficulty` is explicitly rejected with `400 Bad Request`. |
| **Live Progress Streaming** | Deferred to **Week 6** | Real-time WebSocket/SSE progress updates are deferred. Progress is polled on demand via `GET /api/exams/[id]/progress`. |
| **Grading UI & Grade-Save Caller** | Deferred to **Week 7** | Grading evaluation interface and grade submission endpoint are deferred. In Week 7, the grade-save flow will invoke `AllocationService.markCompleted()`. |

## 4. Validation & Demo Checklist

- [x] **No Student PII in Blind Mode**: Verified `student`, `qrStudentId`, `omrStudentId` are omitted when blind grading is active.
- [x] **TA Ownership Scoping**: Verified `GET /api/allocations` strictly scopes results to `auth.user.id`.
- [x] **Oldest-First Queue Ordering**: Verified deterministic ordering by `createdAt` ascending + `_id` ascending.
- [x] **Pagination Support**: Verified `page` and `limit` handling, total count, and totalPages metadata.
- [x] **Claim Transition**: Verified atomic `PENDING` $\rightarrow$ `IN_PROGRESS` state transition.
- [x] **Release Transition**: Verified atomic `IN_PROGRESS` $\rightarrow$ `PENDING` state transition.
- [x] **Professor Override Release**: Verified Professors and Admins can release allocations owned by other TAs.
- [x] **Completion Transition**: Verified `AllocationService.markCompleted()` transitions `IN_PROGRESS` $\rightarrow$ `COMPLETED` idempotently.
- [x] **Progress Aggregation**: Verified server-side `$match` + `$group` pipeline dynamically updates counts from `0/N` to `1/N`.
- [x] **Deferred Functionality**: Verified boundaries for AE-097b (difficulty sorting), Week-6 (live events), and Week-7 (grading UI / save flow).
